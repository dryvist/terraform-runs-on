# GitHub Actions → RunsOn Migration Guide

This guide migrates JacobPEvans repositories from GitHub-hosted runners
(`ubuntu-latest`) to self-hosted RunsOn runners deployed by this repository.
It targets v3 of the RunsOn `flex` Terraform submodule.

Each migrated workflow drops to the EC2 spot price (~$0.03/hr for the default
runner) instead of the GitHub Actions minute multiplier, and runs on dedicated
compute with no queue wait.

## Prerequisites

A repository can opt in to RunsOn runners only after all four are true:

1. The RunsOn CloudFormation stack is applied from the `main/` directory
   (`terragrunt apply` completes and the App Runner URL responds).
2. The RunsOn GitHub App is installed on the target repository. The app
   installation page is reached from the App Runner URL printed by
   `terragrunt output`. The app must list the target repo in its allowlist —
   either by selecting "All repositories" at install time, or by adding the
   repo individually under the App settings page.
3. Migrated workflows reference the v3 RunsOn label format:
   `runs-on=${{ github.run_id }}/runner=...`. The legacy v2 label
   `runs-on=...,runner=...` still parses, but use the v3 format for
   all new migrations.
4. Cost allocation tags are propagated. The Terraform config in this repo
   already passes `cost_allocation_tag = "runs-on"`, which sets the AWS
   `runs-on` tag on every EC2 instance launched. No per-repo action needed.

If a workflow's first migrated run hangs in `queued` state with no runner
ever picking it up, the most common cause is that the app installation does
not have the repo in its allowlist.

## Runner label catalog

RunsOn v3 supports two label styles. The single-string format is used
throughout this org for consistency.

| Workload | Label | Notes |
| --- | --- | --- |
| Default CI step (lint, validate, small build) | `runs-on=${{ github.run_id }}/runner=2cpu-linux-x64` | Matches the smoke-runner canary in this repo. `m8i.large` spot. |
| Nix flake check (Linux only) | `runs-on=${{ github.run_id }}/cpu=4/ram=16/family=m7+c7/extras=s3-cache` | More disk and RAM for nix substitution; `s3-cache` enables the RunsOn S3 cache. |
| Build with large dependency cache | `runs-on=${{ github.run_id }}/cpu=4/ram=16/volume=80gb:gp3:500mbs:4000iops/extras=s3-cache` | Use when default 30 GB volume runs out. |
| Heavy CPU job (terraform plan over many modules, compile-heavy) | `runs-on=${{ github.run_id }}/cpu=8/ram=32/family=c7a` | Compute-optimized. |
| GPU (Hugging Face, MLX cross-eval) | `runs-on=${{ github.run_id }}/family=g4dn.xlarge/image=ubuntu22-gpu-x64` | Currently unused; reserved label for future workloads. |

The `${{ github.run_id }}` segment is **required** so RunsOn can correlate
the `workflow_job` webhook back to the originating run. Omitting it makes
the runner refuse to pick up the job.

The `runner=2cpu-linux-x64` shorthand refers to a named runner declared at
the RunsOn application level — it's the default RunsOn provides out of the
box. The shorthand resolves to roughly `cpu=2,ram=8,family=m7,image=ubuntu24-full-x64,spot=true`.

## What does NOT migrate

| Workflow | Reason |
| --- | --- |
| `_nix-build.yml` (nix-darwin, runs on `macos-latest`) | macOS support in RunsOn requires dedicated EC2 Mac instances with a 24-hour minimum allocation. For short CI builds (~10 min), github-hosted `macos-latest` is cheaper despite the 10x minute multiplier. |
| `deps-update-flake.yml` (nix-darwin, `macos-latest`) | Needs `darwin-rebuild`-related evaluation paths; same cost rationale as above. |
| `*.lock.yml` (gh-aw generated agentic workflows) | Auto-regenerated by `gh-aw compile`. Edits would be reverted on the next pin refresh. If we migrate these, it has to happen in the `.md` companion via a gh-aw runner option (not currently exposed). Their `ubuntu-slim` runner cost is minor; defer until gh-aw supports it natively. |
| Disabled-schedule workflows (`best-practices.yml`, `next-steps.yml`, `review-deps.yml`, `code-simplifier.yml`) | The `schedule:` triggers are commented out; nothing actually runs except manual `workflow_dispatch`. Migrating saves no minutes. |

## Cost expectations

A typical PR in `nix-darwin` exercises:

- `Detect Changes` (~30 s, ubuntu-latest currently)
- `Nix Validate` on Linux (~10 min, ubuntu-latest currently)
- `Markdown Lint` (~30 s)
- `File Size` (~30 s)
- `Claude Settings` (~2 min)
- `Merge Gate` (~5 s)

Total: ~14 minutes of `ubuntu-latest` per PR. At the GitHub-hosted billing
rate of $0.008/min for private repos, that's ~$0.11/PR; public repos are
free up to the free-tier cap, then $0.008/min after.

After migration: ~14 minutes of RunsOn spot at ~$0.03/hr (`m8i.large`)
= ~$0.007/PR. About **15× cheaper** on the private side, and pulls usage
entirely off the GitHub Actions meter on the public side (which is what
this org actually cares about — staying inside the free tier).

Add the fixed infrastructure overhead (see [Cost](../README.md#cost)),
and the breakeven for nix-darwin alone is roughly 50 PRs/month. Adding
nix-ai pushes the math further in favor of RunsOn.

## Migration order

Follow this order to land changes incrementally and verify each step:

1. **Reusable workflows in `JacobPEvans/.github`.**
   Add an optional `runner_label` input (default `ubuntu-latest`) to every
   reusable `_*.yml`. Pass it through where `_ci-gate.yml` calls children.
   No behavior change for existing callers — `ubuntu-latest` stays the
   default until each caller opts in.

2. **Single canary job in `nix-darwin`.**
   In `ci-gate.yml`, change only the `claude-settings` job's `runs-on` line
   (or pass `runner_label` to a single child workflow). Open the PR, watch
   the run complete, verify the runner shows up in the RunsOn dashboard,
   and confirm the spot instance terminated cleanly.

3. **Remaining `nix-darwin` workflows.** Convert `Detect Changes`,
   `Markdown Lint`, `File Size`, `Nix Validate` (Linux only), and the
   `Merge Gate` job itself.

4. **`nix-ai` canary + remaining workflows.** Mirror the same two-PR pattern.

5. **Watch for queue stalls.** The `_ci-gate.yml` watchdog in
   `JacobPEvans/.github` cancels any sibling job stuck in `queued` after
   `queue_timeout_minutes` (default 10). That window is the safety net if
   AWS spot capacity for the requested family is briefly exhausted — RunsOn
   v3's spot circuit breaker will fall back to on-demand, but if even that
   fails the watchdog will keep the merge gate from being blocked forever.

## Rollback

A single-file revert restores the previous behavior. RunsOn-launched spot
instances terminate on their own once the job ends; nothing leaks.

To temporarily route a single workflow back to GitHub-hosted while
investigating, change the label string:

```yaml
runs-on: "runs-on=${{ github.run_id }}/runner=2cpu-linux-x64"  # before
runs-on: ubuntu-latest                                          # after
```

For a wholesale rollback at the reusable-workflow level, drop `runner_label`
from the consumer side; the reusable workflow's `ubuntu-latest` default
takes over again.

## Verifying a migrated workflow

1. Open the run in the GitHub Actions UI. The runner label printed in the
   `Set up runner` group must include `RUNS_ON_VERSION=v3.x.x` and an
   `RUNS_ON_INSTANCE_ID=i-...` line. If those are missing, the job ran on
   github-hosted compute despite the label.
2. Check the RunsOn dashboard at the App Runner URL — the instance should
   appear under "Recent runs" with the right repo, workflow, and job ID.
3. Confirm the instance terminated. RunsOn terminates spot instances when
   the job completes; long-lived instances indicate a bug.
4. Inspect AWS Cost Explorer the next day. Filter by the `runs-on` tag
   group; the migrated repo's spend should appear under its repo name.
